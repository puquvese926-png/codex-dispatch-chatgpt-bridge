# Bridge failure playbook

Use this file when a bridge command fails. Add every novel failure before retrying.

## Required incident record

Record:

- command and exact stage;
- durable status (`not-submitted`, `unknown-after-submit`, `timeout-after-submit`, `not-recovered`);
- whether content may already have been sent;
- safe next action and forbidden action;
- narrow cause and code fix;
- regression test and full-suite result.

Never infer submission from a visible window. Never infer non-submission after a post-submit websocket loss.

## Known failures and prevention

| Symptom / stage | Meaning | Safe response | Preventive rule |
| --- | --- | --- | --- |
| `EPATHCOLLISION` during command preflight, before `discover` | Two command roles are the same after case-insensitive Win32 normalization, canonical `realpath` resolution, physical file identity, or a symlink/junction/reparse alias. The same check also rejects duplicate/hardlinked references and cleanup artifacts. No CDP request, UI action, output write or GPT content was reached. | Keep the result pre-submit and do not delete, rename or “repair” either path automatically. Change the manifest/output layout explicitly, then run a new preflight. Do not retry while the role collision remains. | Parse first, read and strictly validate the manifest once, audit every role before discovery, and fail closed with the conflicting role names. Audit only reads `lstat`/`stat`/`realpath`; missing output/progress/ledger/checkpoint paths are audited from their nearest existing ancestor and are never pre-created. Pass the validated manifest object into the runner; do not reread it by path after discovery. Regression: `path identity normalizes case, dot segments, realpath aliases and missing children`, hardlink/reference collision, derived output/progress/state collision, cleanup artifact collision, and `collision preflight stops discovery and every write`. The residual boundary is TOCTOU after preflight, not covered as hostile filesystem defense. |
| Global bridge silently selects a project-private or stale worktree runtime | The public wrapper retained a legacy project environment variable and ancestor lookup. A task launched inside an old worktree therefore connected successfully but exposed an obsolete schema, making the global Skill appear coupled to that project. | Treat as pre-submit; do not downgrade the payload, send through the selected project runtime, or infer compatibility from `discover`/`probe` alone. | Bundle the runtime in the bridge repository, install it to `%USERPROFILE%\.codex\bridge-runtime\dispatch-chatgpt-bridge`, and resolve only explicit `-Root` → `CODEX_BRIDGE_ROOT` → installed standalone runtime → repository-local runtime. Ignore legacy project variables and never walk ancestor directories. Regression: `standalone-runtime-tests.mjs` verifies runtime bundling, legacy-root rejection and dual Skill/runtime installation. |
| Pre-submit `image-generation ... references must contain 1-8 image attachments` for an original generation job with `references: []` | The schema-v2 validator applied the `image-edit` minimum to both image job types. The request failed before a run ID, conversation, report or `submittedAt` existed even though the attachment and lifecycle paths already handled an empty list safely. | Keep the result `not-submitted`; do not add a meaningless reference image or rerun batch until the validator and contract are synchronized. | Require an explicit references array for every v2 job, allow 0–8 only for `image-generation`, and continue requiring 1–8 for `image-edit`. Non-empty lists retain absolute path, extension, size and SHA-256 verification before chat creation; an empty generation list skips attachment upload and remains `references: []` in the submission report. Regression: `allows original image generation without references while image edit still requires them`, zero-reference attachment/report coverage, lifecycle tests, and the full suite. |
| Standalone bootstrap fails to load `Get-AppxPackage` under PowerShell 7 with `Operation is not supported on this platform` | The Windows `Appx` module is available to Windows PowerShell 5.1 but cannot be loaded in the current PowerShell Core host. The bridge state was not created and no content was sent. | Keep the result pre-submit; do not restart Codex or fall back to a project startup script. | `start-chatgpt-bridge.ps1` must relay its exact bounded parameters to `powershell.exe` whenever `PSEdition` is not `Desktop`, then preserve the child exit code. Regression: the standalone bootstrap test invokes the self-test through both `powershell.exe` and `pwsh.exe` and requires the effective host edition to be `Desktop`. |
| `-RestartExisting` closes Codex, then the initialization command is interrupted; `state.json` is missing and neither `discover` nor `probe` can determine whether restart succeeded | The old startup path stopped the Codex process tree from a PowerShell process launched by that same Codex instance. Closing the parent could terminate or orphan the caller before it activated the replacement and wrote state. A later ad-hoc `Start-Process` child was not a durable handoff guarantee. | Do not repeatedly close Codex and do not infer failure solely from the interrupted UI command. Inspect `%LOCALAPPDATA%\CodexChatGPTBridge\restart-report.json`; wait only while it has a running status, accept success only for `complete` plus `ready: true`, and use the recorded error for `failed`. | Before stopping anything, atomically write a restart request and report, then create the worker through `Invoke-CimMethod Win32_Process.Create` so Windows—not the Codex process tree—owns it. The worker revalidates the exact Store package and captured PIDs, stops only those PIDs, starts Codex with loopback CDP arguments, waits for the verified endpoint, writes `state.json`, and seals the report. Regression: `standalone-runtime-tests.mjs` requires the detached strategy and durable report contract; full suite must pass without actually restarting Codex. |
| Host clipboard read/write fails while a remote-control clipboard proxy owns it (`UURemoteClipboard`) | The remote-control client kept a hidden clipboard window open, so native `Clipboard.SetText` failed and every application appeared unable to copy or paste; this is host transport state, not a bridge composer or GPT route failure. | Do not send prompts through the visible UI and do not resend a job. Verify the exact owner class/process, then restart only the remote-control client if the user accepts a brief disconnect; keep its service running. | Re-test native clipboard round-trip after restart, confirm the owner window is gone, and keep bridge payloads file-based JSON so generation does not depend on host clipboard health. |
| `Runtime.evaluate` timeout during quick-chat open | Native open RPC may wait on renderer lifecycle; making the inner JS promise nonblocking is insufficient if CDP still uses `awaitPromise: true`. | If no `submittedAt`, diagnose and retry only under the original authorization. | Dispatch the lifecycle expression with CDP `awaitPromise: false`; verify the selected renderer and exact route independently. |
| Prewarm renderer reused or rebuilt unexpectedly | Electron may reuse the prewarm target or replace it with one new app page. | Stop before send when target identity is ambiguous. | Select only the exact prewarm target or one uniquely attributable rebuilt app target; never close user windows. |
| Attachment acknowledgement timeout or ambiguous attachment control | Upload may have reached a file input, but a global first-match button/input, repeated attachment click, whole-root text search or filename-only check could belong to Codex, another dialog, a history message, or a portal outside the leased ChatGPT owner. | Stop before send; keep the job `not-submitted`; do not assume references were attached or retry automatically. | Bind the attachment button, exact single `input[type=file]`, `DOM.setFileInputFiles` node and acknowledgement to the prepared surface/conversation owner. Click the attachment control at most once, then poll a read-only exact-root input count; fail immediately on a count above one. Resolve the input as a Runtime remote object, map it with `DOM.requestNode`, release it on success/failure, and accept only that owner's `input.files` or visible attachment/file-semantic `aria-label`, `title`, `img alt` or explicit attachment/file `data-testid` for every expected basename. Original generation with `references: []` makes no attachment UI/CDP calls. Regression: exact-root attachment button/input/state/acknowledgement, one-click delayed input, ordinary-text and remote-object release tests; snapshot/approve are outside this fix. |
| Image result is `metadata-only`, or an image is rejected during materialization | The old persistence path fetched renderer-provided HTTP(S) URLs with redirect following and decoded unbounded data/base64 before validating the result. That created SSRF and memory/file risks, and DOM dimensions/content types were not a trustworthy provenance or format boundary. | Keep the job result and report; do not retry a remote URL or interpret metadata-only as a local artifact. A remote-only image needs renderer-provided materialized data or a user-supplied local save. No GPT resend is implied. | Persist only strict PNG/JPEG/WebP data URLs, or exact `blob:app://-/<strict-id>` values first materialized by the exact renderer into PNG data. Never fetch HTTP(S), loopback, metadata, redirect-shaped or `blob:https` sources. Reports distinguish `sourceType: "renderer-data-url"`, `"materialized-app-blob"` and `"remote-image"`; remote metadata is bounded and reports omit URLs/base64. Regression: `chatgpt-image-materialization-tests.mjs` proves zero fetches/files for remote sources, exact provenance and fail-closed malformed/oversized/aggregate materialization. |

## Retry gate

Before any retry, answer all of these in the report or task notes:

1. Was the original job submitted?
2. Is the next operation send-capable or read-only?
3. What exact stage failed?
4. What changed since the previous attempt?
5. Which test proves the change?
6. Does the next attempt risk duplicate generation?

If any answer is unknown, fail closed. A user may explicitly authorize a different fresh job, but it must receive a new conversation, job ID, marker and lifecycle entry; the ambiguous original remains untouched.

## Detached launch handle is missing, corrupt, or reports `report-corrupt` / `progress-corrupt`

`-Detach` is a durable handoff, not a promise that the parent shell remains alive. The
returned `launchPath` is the only authoritative handle. `batch` owns a real
`<report>.progress.json`; `resume` and `watch` deliberately have no progress sidecar.
If `status` or `wait` cannot strictly read the launch JSON, or finds an existing report
or progress file that is malformed/oversized, it returns a structured failure instead of
silently treating the file as absent. PID reuse is rejected by comparing the recorded
process start time. Each final Node command line also carries the unique launch UUID;
PID attribution uses that token, not the report path, so equal output paths cannot
cross-adopt a process.

If Windows created the detached final Node process but it could not be uniquely
attributed, the launch is `starting` with `errorClass: created-but-unattributed`
and `unknown-after-launch`. `wrapperPid` is retained as a legacy diagnostic alias;
on the current direct CIM path it equals the final Node PID, not a second worker
PID. This is an ambiguous post-launch state: do not mark it as `not-created`, do
not start a replacement batch, and do not retry automatically. Only a proven
final-process creation failure is `not-created`/`failed`.

The public `stdoutPath` and `stderrPath` are the launch-directory logs of that
same final Node process, not worker or wrapper logs. A pre-report crash should
leave a bounded JSON error in `stderrPath`; its presence is diagnostic only and
does not make an ambiguous launch retryable.

Safe response: preserve the launch directory and business files, do not start another
batch, and do not infer success from a visible window. Re-run `status` with the exact
`launchPath`; inspect the bounded JSON summary and logs without editing the launch record.
Only an explicit, separate user authorization may create a new job. `status`/`wait` are
runner-only read paths and do not require the deployment manifest, start Node, connect
CDP, resume, resend or delete.

This is the supported semi-automatic path: `plan -> explicit authorization -> detach ->
status/wait -> report or one read-only recovery decision`. It is not a permanent daemon,
automatic GPT reply service or cryptographic proof of user approval. Regression:
detached batch/resume/watch handle shape, truthful progress path, runner-only status/wait,
path-bound/corrupt/oversized launch rejection, PID start-time mismatch, corrupt
report/progress visibility, bounded wait, start-failure record and ambiguous recovery
summary tests.

## `BRIDGE_BATCH_UNKNOWN_AFTER_SUBMIT`

This user-facing error is a post-click ambiguity, not permission to resend. Find the
original durable report and its `<report>.progress.json` sidecar first. Preserve the
original job ID and copy its exact `surface`, `conversationId`, `marker`,
`promptHash` and, when captured, the unique `historyTitle` into one read-only resume
manifest. Run `run-bridge.ps1 -Action resume` without `-AllowSend`, using a new
resume report path. Accept only a result that proves the same marker inside the same
conversation identity.

If the route, title or marker is unavailable, the only honest outcome is
`not-recovered`; do not promise retrieval, close/delete the original conversation or
start a replacement batch. A genuinely new generation requires a separate explicit
user authorization and a new job/conversation; the ambiguous original remains sealed.
This is a bounded recovery path, not a persistent daemon or automatic GPT reply service.
The MVP supports explicit dispatch and read-only recovery; it does not make itself a
background listener by editing `AGENTS.md`.
